At Phase 19's start the operator split it into three children. Preflight's Step 1a says to draft only the first child and lets close.md Step 9a draft the next one; but acceptance.md's prospective child close requires the next real child and its ledger row to be drafted and captured *before final review*, because a child may close only beside an active parent with another drafted incomplete child. Following Step 1a literally captured a ledger with 19.1 alone, so the run had to park before its critique and continue in a fresh run after 19.2 was drafted.

Do differently: when a decomposition already names the next child (the operator listed all three here), draft it and its ⏳ row together with the first child, before authority capture. Preflight Step 1a and close Step 9a disagree on when the successor is drafted; the methodology should state that a known successor is drafted at entry.
